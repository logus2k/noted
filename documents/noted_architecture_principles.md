## 1. Purpose

This document codifies the architectural principles that govern all design and implementation decisions in noted. These principles exist to prevent scope creep, ensure long-term maintainability, and guarantee that noted remains a useful tool rather than a vendor trap.

Every new feature, integration, and technical decision should be evaluated against these principles. When principles conflict, the ordering in this document reflects their priority — earlier principles take precedence.

---

## 2. Principles

### P1: Zero Vendor Lock-In (The Eject Button)

**Statement:** A user who uninstalls noted must be left with a fully functional MLOps stack. Every artifact noted creates or manages must work without noted.

**Rationale:** noted integrates tools that practitioners already use and that organizations already trust. If noted becomes a dependency that cannot be removed without breaking workflows, it ceases to be an integration layer and becomes a prison. The value proposition is convenience, not captivity.

**Rules:**

- **Notebooks** are standard `.ipynb` (nbformat 4). Custom metadata (Run Manager definitions, cell run membership) is stored in the `metadata` dict, which Jupyter and other tools silently ignore. Opening a noted notebook in JupyterLab works without errors.
- **MLflow runs** are standard MLflow runs. Tags injected by noted (`instrumentation: auto`, `dvc.data_hash`, `hydra.config_hash`) are ordinary MLflow tags — queryable, deletable, and meaningful outside noted. No custom MLflow plugins.
- **DVC tracking** uses standard DVC commands and `.dvc` pointer files. The MinIO remote is configured via standard DVC remote config (`dvc remote add`). Running `dvc push` and `dvc pull` from a terminal works identically to running them from noted's UI.
- **Hydra configs** are standard YAML files in the project's `conf/` directory, following Hydra's config group conventions. No noted-specific schema, no custom OmegaConf resolvers, no proprietary config format. A script decorated with `@hydra.main` runs from the command line exactly as it does inside noted.
- **Airflow DAGs** — whether generated by noted or authored by the user — contain only standard Python and standard Airflow operators (`BashOperator`, `PythonOperator`, `@task`). No `noted-airflow-sdk`, no custom operators, no imports from `noted.*`. If noted is removed, DAGs continue to execute on the raw Airflow infrastructure without modification.
- **Git repositories** managed by noted's backend are standard bare Git repos. They can be cloned, pushed to a remote, and interacted with using any Git client.
- **MinIO buckets** follow standard S3 conventions. Any S3-compatible client can read and write to the same buckets noted uses.

**Test:** For every feature, ask: *"If noted disappears, does the user's work survive intact?"* If the answer is no, the design is wrong.

### P2: Backend Services Stay Canonical

**Statement:** MLflow, Airflow, MinIO, DVC, and Git are the sources of truth. noted never duplicates their state into its own database.

**Rationale:** Duplicated state drifts. If noted maintains a parallel database of experiment runs, it will eventually disagree with MLflow, and the user will not know which to trust. The canonical source for each domain is the tool that owns it.

**Rules:**

- Experiment data is always fetched from the MLflow API, never cached in noted's PostgreSQL database.
- Pipeline state is always fetched from the Airflow API.
- Object metadata is always fetched from the MinIO S3 API.
- Data version state is always derived from `.dvc` files and Git history.
- noted's PostgreSQL database (`noted` schema) stores only UI metadata: layout preferences, tab state, user sessions, activity feed events. It never stores experiment metrics, run parameters, data hashes, or pipeline definitions.

**Exception:** Short-lived client-side caches with TTL (for UI responsiveness) are acceptable, but they are never treated as authoritative.

### P3: Integration Over Aggregation

**Statement:** noted is a purpose-built interface that communicates with backend services through their APIs, not a dashboard that embeds other tools' UIs.

**Rationale:** Embedding iframes of MLflow, Airflow, and MinIO web UIs would be aggregation — faster to build, but the user experience is a patchwork of inconsistent interfaces with no cross-tool workflows. Integration means building noted's own views that compose data from multiple services into coherent experiences (e.g., a run detail view that shows MLflow metrics, DVC data version, Hydra config, and Airflow pipeline status together).

**Rules:**

- Service UIs (MLflow, Airflow, MinIO) are accessible as iframe tabs in the center pane for advanced use and as an escape hatch, but they are not the primary interaction model.
- Primary workflows (log a run, compare experiments, trigger a pipeline, promote a model) are native to noted's UI.
- Cross-service features (e.g., viewing the data version used in an experiment run) are first-class — they are the reason noted exists.

### P4: Explicit Over Magical

**Statement:** Every action noted takes on behalf of the user is visible and understandable. No hidden side effects.

**Rationale:** Trust is earned through transparency. If noted silently modifies kernel code, injects environment variables, or commits files to Git, the user must be able to see what happened and understand why.

**Rules:**

- **Auto-instrumentation** injects MLflow code into the kernel, but all auto-runs are tagged `instrumentation: auto` (or `instrumentation: run_manager`) so they are clearly distinguishable from explicit user code. The injected code is documented and inspectable.
- **Environment injection** (`MLFLOW_TRACKING_URI`, `MLFLOW_EXPERIMENT_NAME`, `PYTHONPATH`, `LD_LIBRARY_PATH`) happens at kernel startup. The injected variables are listed in the kernel info panel.
- **DVC operations** (add, push, commit) triggered from the UI produce visible results: workspace tree badges update, Source Control panel shows the new commit, toast notifications confirm the action.
- **Run Manager badges** on cells are always visible (not hidden behind a panel toggle), so the user always sees which cells belong to which runs.
- **No files behind the curtain.** Every file noted creates — `.dvc` pointer files, Git commits, Hydra output directories, Airflow DAG files — is visible in the workspace tree.

### P5: Progressive Complexity

**Statement:** A new user can open noted, create a notebook, write Python, and execute cells — exactly like Google Colab. MLOps features are discovered organically as needs grow.

**Rationale:** Frontloading the full MLOps stack onto a first-time user creates overwhelm. The notebook experience must be simple and complete on its own. Data versioning, experiment tracking, and orchestration are power features that appear when the user is ready.

**Rules:**

- The default workspace shows Projects and Environments. Other sections (Experiments, Storage, Pipelines, Models, APIs) appear when relevant services are connected or when the user first interacts with them.
- Empty states in every workspace section guide the user to the next action: *"Run a cell with MLflow tracking to see results here"*, *"Upload your first dataset to get started"*.
- The notebook editor works fully without MLflow, DVC, Hydra, or Airflow. These integrations enhance but do not gate the core experience.

---

### P6: The Terminal Is an Escape Hatch

**Statement:** When infrastructure operations fail in ways the UI cannot handle, the built-in terminal (xterm.js) is the explicit fallback — not a complex UI for every edge case.

**Rationale:** Git and DVC can fail in arbitrarily complex ways: merge conflicts on `.dvc` files during concurrent data uploads, DVC cache corruption, lock file contention, rebase failures. Building UI for every failure mode is an unbounded scope expansion that will never converge. The terminal already exists and can handle any scenario.

**Rules:**

- noted's UI covers the happy path for Git and DVC operations: init, add, commit, push, pull, tag, status, diff. These are the operations that happen dozens of times a day and benefit from a visual interface.
- When `ProjectVersionControl` or `DvcManager` catches a non-standard error (merge conflict, lock contention, corrupt cache, unrecognized state), the UI shows a clear toast notification describing the problem and offering an **"Open Terminal"** action button.
- The terminal opens pre-navigated to the project directory (`cd /path/to/project`) so the user lands in the right context immediately.
- noted does **not** build:
  - A merge conflict resolution UI (GitHub-style 3-way merge viewer)
  - A DVC lock manager
  - A Git rebase/cherry-pick visual interface
  - Automatic conflict resolution heuristics
- The terminal is not a failure mode — it is a designed escalation path. The UI handles routine operations; the terminal handles the exceptions.

**Implementation:**

```javascript
// When a Git/DVC operation fails unexpectedly
Notify.error('DVC push failed: lock file exists.', {
    action: { text: 'Open Terminal', callback: () => openTerminal(projectPath) }
});
```

### P7: Single Container, Proxy Pattern

**Statement:** noted runs as a single Docker container. The browser communicates only with noted. All backend service calls are proxied through the noted backend.

**Rationale:** This pattern centralizes secrets management (MinIO keys, Airflow JWT tokens never reach the browser), enables cross-service orchestration as atomic backend operations, simplifies deployment (one container to manage), and provides a single point for authentication when it is added.

**Rules:**

- The frontend makes HTTP and Socket.IO calls to noted's backend only. No direct XMLHttpRequest or fetch to `mlflow:5000`, `airflow-apiserver:8080`, or `minio:9000`.
- Pre-signed URLs for large artifact downloads are the one exception — they are generated by the backend but fetched directly by the browser from MinIO, to avoid proxying multi-GB model files through the backend.
- The backend exposes REST endpoints (`/api/...`) and Socket.IO events that abstract the underlying service APIs. Frontend code never constructs MLflow, Airflow, or MinIO API calls.

---

### P8: Event-Driven, Not Polling

**Statement:** All real-time updates are pushed via Socket.IO. No `setTimeout`-based polling on the frontend.

**Rationale:** noted already has a mature Socket.IO infrastructure for collaboration (cell updates, lock state, kernel status, user presence, execution output streaming). Extending this to MLOps events (metric updates, pipeline state changes, model promotions) is natural and efficient.

**Rules:**

- The backend may poll external services (MLflow API for new metrics, Airflow API for task state) at controlled intervals, but the results are pushed to the frontend via Socket.IO events.
- The frontend subscribes to events and updates reactively. No `setInterval` for UI refresh.
- Event payloads include enough data for the frontend to update without a follow-up API call (e.g., a `metric:update` event includes the metric name, value, step, and timestamp — not just a "something changed" signal).

**Exception:** The Airflow pipeline monitoring backend polls the Airflow API at a 2-second interval during active runs. This is backend-side polling converted to frontend-side push — the frontend itself does not poll.

---

### P9: Collaboration as Default

**Statement:** Every feature is designed for multi-user scenarios from the start, not retrofitted later.

**Rationale:** noted already has real-time collaboration (cell locking, TTL leases, Socket.IO presence, room-based broadcasting). Building new features without considering multi-user behavior creates race conditions and inconsistent state that are expensive to fix later.

**Rules:**

- All state-changing operations (DVC track, MLflow run creation, model promotion, pipeline trigger) emit Socket.IO events to all connected clients in the same project room.
- Git/DVC operations are serialized per project via the existing lock pattern.
- The activity feed records all significant actions with user attribution.
- Two users viewing the same experiment list see the same runs appear in real time when either of them starts a training run.

---

### P10: No Framework, No Build Step

**Statement:** The frontend is vanilla ES6 modules served as static files. No React, no Vue, no Angular, no webpack, no Vite.

**Rationale:** The frontend is already built this way and it works. Introducing a framework would require a complete rewrite of all existing UI code (3500+ lines in ExplorerPanel.js alone), add a build step that slows development, and introduce a framework upgrade treadmill. The current approach — direct DOM manipulation, ES6 classes, CSS modules — is verbose but predictable, debuggable, and dependency-free.

**Rules:**

- All frontend JavaScript is served directly from `frontend/js/` as ES6 modules. No transpilation, no bundling (except the CodeMirror vendor bundle).
- Third-party libraries (jsPanel, Wunderbaum, Split.js, xterm.js, Notyf, marked.js, KaTeX, pdf.js) are loaded as vendor scripts, not npm dependencies.
- CSS is organized as per-component modules (`base.css`, `cell.css`, `explorer-panel.css`, etc.) with CSS custom properties for theming.

**Exception:** CodeMirror 6 requires a pre-built ESM bundle (`frontend/vendor/codemirror/codemirror.bundle.js`) because its module system is incompatible with direct browser imports. This bundle is committed to the repository and only rebuilt when CodeMirror is updated.

## 3. Principle Application Checklist

Before merging any significant feature, verify:

| # | Check | Principle |
|---|-------|-----------|
| 1 | Does the user's work survive if noted is removed? | P1 |
| 2 | Is the source of truth an external service, not noted's database? | P2 |
| 3 | Is this a native view, not just an iframe of another tool? | P3 |
| 4 | Can the user see and understand what noted did on their behalf? | P4 |
| 5 | Does the feature work without requiring MLOps knowledge? | P5 |
| 6 | For infrastructure failures, does the UI escalate to the terminal? | P6 |
| 7 | Does the browser only talk to noted's backend? | P7 |
| 8 | Are updates pushed via Socket.IO, not polled from the frontend? | P8 |
| 9 | Does this work correctly with two concurrent users? | P9 |
| 10 | Is this vanilla ES6 with no build step? | P10 |

## 4. Anti-Patterns

These are patterns that have been explicitly considered and rejected:

| Anti-Pattern | Why Rejected | Principle |
|---|---|---|
| Custom `noted-airflow-sdk` with proprietary operators | Generated DAGs must run on raw Airflow without noted | P1 |
| Custom OmegaConf resolvers (e.g., `${dvc:path}`) | Hydra configs would break outside noted | P1 |
| Caching MLflow run data in noted's PostgreSQL | State duplication leads to drift | P2 |
| Building a merge conflict resolution UI | Unbounded scope; terminal handles it | P6 |
| Building a DVC lock file manager UI | Rare edge case; terminal handles it | P6 |
| Frontend polling MLflow API directly | Violates proxy pattern and pushes secrets to browser | P7 |
| `setTimeout`-based UI refresh for pipeline status | Use Socket.IO push from backend | P8 |
| Introducing React/Vue for a single component | Inconsistent stack, build step dependency | P10 |
| Custom authentication service in FastAPI | Solved at nginx layer (OAuth2-Proxy/Authelia) | Out of scope |

## 5. Decisions Log

Significant architectural decisions and their rationale:

| Decision | Options Considered | Chosen | Rationale | Date |
|---|---|---|---|---|
| Git implementation | pygit2, git subprocess | git subprocess | Simpler, works reliably in container, no C library dependency | 2026-03-10 |
| Airflow worker data access | Volume mount, DVC pull per task | Shared volume mount (read-only) | Lower latency, no DVC dependency in worker image | 2026-03-10 |
| Airflow API auth | Basic auth, session, JWT | JWT tokens via `/auth/token` | Airflow 3.x standard, stateless | 2026-03-10 |
| Frontend framework | React, Vue, vanilla ES6 | Vanilla ES6 | Already built, no rewrite needed, zero build step | Pre-project |
| MLflow metric streaming | Kernel-level intercept, API polling | API polling (1s interval) | Simpler, no kernel modification, optimize later if needed | 2026-03-12 |
| DVC mode | `--no-scm`, full SCM | Full SCM (Git backend) | Preserves `dvc repro`, `dvc diff`, pipeline caching, branching | 2026-03-10 |
| Authentication | Custom FastAPI auth, OAuth2-Proxy at nginx | OAuth2-Proxy at nginx (planned) | Zero Python code, protects entire application, standard SSO | 2026-03-14 |
| Git/DVC error handling | Full UI for every failure, terminal escape hatch | Terminal escape hatch | Bounded scope, xterm.js already built, handles any scenario | 2026-03-14 |
| Hydra-DVC synergy | Custom OmegaConf resolver, runtime injection | Runtime injection only | Avoids lock-in (P1); DVC hash logged to MLflow at run time | 2026-03-14 |
